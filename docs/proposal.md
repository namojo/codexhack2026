# 아직 여기 — 미확인 구조 요청을 남기는 인계 검증 하네스

집중호우로 고립된 주택·다세대 건물에서 여러 신고와 현장 보고가 들어올 때, **어떤 요청이 누구의 근거로 확인되었고 어떤 요청이 아직 남았는가**를 대조한다. 공식 119 시스템과 연결하지 않는 synthetic 데이터 기반 해커톤 데모다. 공개된 다매체 신고 채널 구성을 참고한다. [공개 출처와 접근 한계](sources.md)를 보존했다.

## 사용자의 한 가지 작업

주 사용자는 모의 상황실의 인계 담당자다. 교대 직전 미확인 요청 목록을 읽고, 요청 원문·현재 인원·위치·현장 보고를 대조하여 새 담당자에게 넘길 확인 질문을 남긴다. 보조 사용자는 모의 현장팀 보고자와 검증 담당자다. 재난 범위는 집중호우로 인한 주택·다세대 고립 하나로 제한한다. 구조 우선순위, 의료 처치, 대피 경로를 생성하지 않는다.

예를 들어 같은 건물 201호 세 명과 202호 두 명이 각각 신고했는데 현장팀이 “이 건물 세 명 구조”라고 보내면, 건물 전체를 완료 처리하는 대신 두 요청 ID를 유지하고 누구를 구조했는지 묻는다. 201호 근거를 추가로 확인하여 담당자가 세 명 완료를 확정하더라도 202호 두 명은 열린 요청으로 인계한다. 이를 `same-building`의 중간·최종 assertion으로 검사한다.

## 다매체 입력의 공통 표현

공개 안내는 앱·SMS/MMS·영상통화·인터넷 신고 채널을 설명한다. 이 하네스는 그 채널을 실제 통신 연결 없이 다음 합성 이벤트로 매핑한다. [정책브리핑의 채널 안내](https://www.korea.kr/multi/visualNewsView.do?newsId=148931185)

| 입력 | 모의 데이터와 보존 필드 | 확인할 위험 |
|---|---|---|
| 문자 `sms` | 원문, 개별 request_id, 발생·수신 시각 | 오타·외국어, 정정, 다른 가구 구분 |
| 사진/영상 첨부 `mms` | 텍스트 미디어 설명, captured_at, readable, 모의 transcript 및 출처 | 해석 불가, 과거 촬영 내용의 늦은 도착 |
| 앱 `app` | 원문과 GPS subject/accuracy/captured_at | 신고자와 구조 대상 위치가 다른 대리 신고 |
| 영상통화 `video_call` | 텍스트 설명과 인간작성 모의 전사 | 영상 이해를 완료 증거로 오인 |
| 인터넷 `web` | 합성 접수 원문과 request_id | 문자와 재신고가 중복 후보인 경우 |
| 현장 `field` | 개별 후보 요청 ID와 구조/안전 보고 | 부분 구조, 모호한 건물 보고, 다른 팀 인계 |
| 담당자 `operator` | actor와 배정·연결·완료 결정 및 revision | 배정과 완료 혼동, 오래된 승인 |
| 시스템 `system` | 무응답·전송실패의 명시적 이벤트 | 발송 시도·연락 두절을 완료로 오인 |

`field`, `operator`, `system`은 자체 운영 입력이며 공식 신고 채널이라고 주장하지 않는다. 앱 GPS의 신고자 위치 설명은 [공식 소방서 공지](https://gfsa.gwd.go.kr/sc119/partici/partici_news?articleSeq=11097586)를 참고했으며 공식 API·데이터 형식을 가정하지 않는다.

## AI가 필요한 부분과 확정 책임

같은 요청이 자연어로 다르게 표현되고 시간·인원·위치가 여러 메시지에 흩어진다. AI의 역할 후보는 원문을 분석 계약의 관찰로 정리하고, 관련 후보·불일치·추가 확인 질문을 제시하는 것이다. 원문 evidence_quote를 요구하고 없는 근거나 계약 밖 필드는 거절한다. 규칙 엔진은 접수 ID 보존·revision·완료 허용 조건을 검사한다. AI 제안 자체는 담당자 완료 권한을 갖지 않는다.

MVP의 기본 실행은 `fixture`: 사람이 작성한 결정적 분석을 주입한다. 실제 LLM·OCR·ASR 실행 없이도 위험한 상태 전이를 검증한다. `live`는 원문과 직전 상태만 모델에 보내고 fixture/expectations를 노출하지 않는 별도 평가 모드다. 분석 실패·누락은 명시적으로 거절하고 fixture로 보충하지 않는다. 사진·영상은 텍스트 설명이며 영상통화는 모의 전사다. 픽스처 재생 성공은 실제 언어·영상·음성 모델의 정확도가 아니다.

## 완료와 교대 인계

카드는 `open → dispatched → awaiting_confirmation → resolved`의 흐름을 보여준다. 보고 수신만으로 resolved가 되지 않는다. 담당자 결정은 현재 접수 인원, 현재 revision, 이미 도착한 해당 요청의 구조/안전 근거를 대조해야 한다. 결과는 구조 `rescued`, 자력 대피 `self_evacuated`, 타 팀 인계 `transferred`를 구분한다. 자력 대피와 인계도 담당자 확인이 필요하다.

교대 때 넘길 것은 요청 ID·원문 이벤트 목록·현재 사람 수·위치와 시각·미확정 상태·활성 알림 질문이다. 중복 연결은 canonical_id 관계만 남겨 두 원본을 유지한다. 연락 두절·판독 불가·전송 실패는 확인 과제로 남긴다. 완료 뒤 새 위치·인원·도움 정보가 들어오면 다시 확인 상태로 열고 변경 근거를 보인다. 인원 정정은 묵시적 덮어쓰기 대신 정정 이력을 남긴다.

## 장점과 증명 범위

현재 증명 대상으로 삼는 장점은 같은 입력을 반복 재생했을 때 위험한 자동 완료·정보 덮어쓰기·자동 병합을 발견할 수 있고, 담당자가 근거를 따라갈 수 있다는 점이다. 20개 사례의 91개 assertion 중 38개는 위험한 중간 상태를 대상으로 한다. 17개 `input_case`와 3개 `output_fault`는 별도로 분류한다. 오류 주입은 인젝션에 따른 계약 밖 분석·허위 근거·분석 누락을 회귀 검사하는 것이며 live 정확도 분모에서 기본 제외한다.

각 실행은 입력 SHA256·모드·명령·이벤트 snapshots·checks를 보존한다. 실제 통과 수는 실행 결과를 확인한 뒤 보고한다. 생존율·정확도·시간 절감·현장 효율 향상은 미측정이다. 실사용 인계 개선 주장은 담당자 비교 실험과 현장 협의가 필요하다. INSARAG 공개 양식 목록은 [장소 보고와 대상 기록의 구분을 검토할 참고](https://insarag.org/guidance-notes/forms/forms/)로만 쓰며 표준 인증·준수 주장은 하지 않는다.

## 48시간 MVP와 후속

| 시간 | 메인/통합 담당 | 엔진 담당 | 사례/문서 담당 | 독립 QA 담당 |
|---|---|---|---|---|
| 0–6h | 공통 계약·소유권·실행 패킷 고정 | 상태·분석 검증 경계 설계 | 공개 출처 확인, 핵심 위험 목록·합성 원문 | 계약 기반 음성·위치·권한 경계 검사 설계 |
| 6–18h | CLI·브라우저 뷰와 근거 패널 | 표준 라이브러리 결정적 replay·revision·사람 결정 | JSON 20개와 중간 기대값 작성 | 오류·누락·상태 전이 검사 작성 |
| 18–30h | 전체 사례와 데모 통합, 실행 SHA 보존 | 통합 실패 원인 수정 | 사례집·제안서·5분 대본, 기대값 재검증 | 전체 fixture·경계 검사 독립 실행 |
| 30–42h | 실제 브라우저 조작과 live 별도 실행 가능성 확인 | QA가 찾은 엔진 결함 수정 | 근거 인용·시각·문서 수치 일치 점검 | 고친 부분 재검증, PASS/FAIL/NOT_RUN 분리 |
| 42–48h | 입력 지문·산출물·모드·미실행 범위 발표 | 결정적 재생 인계 | 핵심 3사례 리허설·전체 탐색 인계 | 독립 검증 보고와 최종 차단 항목 |

역할은 현재 세션 설정을 상속하며 모델·전역 권한을 바꾸지 않는다. 각 담당자는 배정 경로만 수정한다. 이 표는 작업 배분 계획이며 완료 기록을 대신하지 않는다.

MVP는 합성 사례·결정적 엔진·CLI·사건별 브라우저 근거 보기·독립 QA·실행 지문을 제공한다. 후속은 별도 합성 평가셋의 실제 모델 출력, OCR/ASR 입력 파이프라인의 출처 검증, 담당자 인계 비교 실험이다. 실제 개인정보나 신고 연동은 현 범위에 포함하지 않는다. 공식 시스템 연결 가능 여부와 승인·보안·데이터 계약은 별도 협의 전까지 미확인이다.
