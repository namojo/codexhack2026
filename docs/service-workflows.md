# 상황실 콘솔 사용자 흐름과 합성 업무 데이터

이 콘솔의 신고 원문·인물·팀·도로명·주소·시각·사진·음성은 가상 사례다. 공식 119 시스템이나 내부 양식을 복제한 제품이 아니며 실제 신고·외부 발송·출동 명령을 수행하지 않는다. 담당자가 지정한 우선도와 기록된 업무 상태를 보여 주며 구조 우선순위나 의료·대피 지시를 생성하지 않는다.

현재 정보 대조는 규칙 기반이다. 음성 전사는 미리 작성한 합성 대본이고 사진 설명은 합성 장면의 caption이다. 실제 ASR·OCR·영상 이해 모델을 실행한 결과가 아니다. 실제로 생성한 사진과 음성 파일을 이미지·오디오로 열람할 수 있지만 이 사실이 대상 안전이나 모델 정확도를 증명하지 않는다.

## 첫 화면에서 인계할 사건 찾기

상황 대시보드에서 미처리·확인 필요·처리 완료와 팀 배정을 읽는다. 검색과 상태·채널 필터를 조합하여 사건을 찾고 사건 번호를 열어 원문을 확인한다. 초기 데이터는 2026-10-08의 사건 10건과 가상 팀 4개다. 출동·현장 도착·구조 진행에 각 한 팀씩 총 3팀이 배정되어 있으며 지원팀 한 팀은 가용이다. 완료 후 해당 팀이 해제되면 다른 사건에 배정할 수 있다. 배정은 완료가 아니다.

## 접수부터 현장 진행까지

신고 등록에서 제목·위치·원문을 입력하고 채널·인원·우선도를 확인한다. 실제 파일을 붙이면 허용 형식과 크기, 파일 존재 검사를 거쳐 첨부로 남는다. 음성/사진 아이콘만으로 자료가 있는 것처럼 표시하지 않는다. 접수 후 사건 상세에서 원문과 첨부를 열어 보고 규칙 기반 확인 사항을 읽는다.

진행 변경에서 가용 팀을 배정하고 출동→현장 도착→구조 진행을 기록한다. 진행 note는 담당자가 확인한 사실을 적는다. 팀은 동시에 두 사건에 배정할 수 없으며, 현재 사건에 배정된 팀만 진행 기록에 사용할 수 있다. 출동과 현장 도착이 인원·위치 대조를 대신하지 않는다.

같은 건물 201호와 202호는 개별 사건으로 남는다. 건물 전체 보고 한 건을 두 세대의 전원 구조 근거로 사용하지 않는다. 현재 서비스는 모호한 동일인·가구를 자동 병합하거나 완료를 전파하지 않는다.

## 추가 원문·정정·부분 구조

추가 정보 등록에서 SMS·음성 전사·사진 설명·앱 진술이나 현장 보고를 사건에 추가한다. 각 원문 ID, 작성자, 발생·접수 시각과 첨부는 그대로 보존한다. 인원·위치를 바꾸려면 정정 종류 또는 이유를 적은 수정으로 명시한다. 기존 값은 감사 이력에 남는다.

INC-20261008-003을 열면 접수 원문은 세 명, REP-003-03의 현장 구조 보고는 두 명이다. 접수 인원을 두 명으로 줄여 이 보고를 전원 완료로 만드는 흐름은 허용되지 않는다. 현장 보고 두 명으로 처리 결과를 확정하면 인원 대조 오류를 확인한다. 현재 접수 세 명으로 입력하더라도 근거 보고 두 명과 다르므로 완료가 차단되어야 한다. 새 전원 현장 보고를 등록한 뒤 그 근거와 현재 인원을 담당자가 대조한다. 숫자가 다른 복수 보고를 단순 합산하지 않는다.

INC-20261008-005의 앱 원문은 신고자 휴대폰 위치가 어머니 집이 아니라고 말한다. 대상 주소는 푸른빌라 302호 원문을 유지하고 신고자 GPS로 덮지 않는다. INC-20261008-006의 재연락 응답 없음도 안전·대피·사망·완료의 근거로 해석하지 않는다.

## 결과 확인과 수정 이력

처리 결과 확인에서 해당 사건의 field 보고 하나를 근거로 선택한다. 현재 접수 인원과 근거 보고 인원이 같고 담당자가 대상·전원 결과를 대조한 뒤 rescued·self_evacuated·transferred 중 결과를 정한다. note에 확인한 내용을 남기면 closed 상태와 담당자·확정 시각이 저장되고 팀이 해제된다. 과거 revision 화면에서 보내는 결정은 409 오류로 막혀야 한다.

INC-20261008-008은 10:40 세 명 인계 결과를 확정한 뒤 11:05 새 도움 요청으로 재개했다. 이전 transferred 결과의 근거 REP-008-02와 재개 사유는 outcome_history에 남는다. 11:15 전원 구조 보고 REP-008-04를 대조하여 11:20 현재 rescued를 다시 확정했다. INC-20261008-009는 이동 의향만으로 닫지 않고 11:45 현장 한 명 확인 REP-009-02 후 11:48 self_evacuated를 확정했다.

잘못된 결과를 고칠 때는 처리 완료 사건을 이유와 함께 재개한다. 이전 결과를 삭제하거나 직접 덮어쓰지 않는다. 이후 새 현장 보고와 현재 인원을 대조하여 재확정한다. 완료 사건에 추가 신고·중요 인원/위치 변경이 오면 자동 reviewing으로 돌아간다. INC-20261008-010은 12:24 두 명 rescued를 확정했지만 12:45 세 명 인원 정정 원문 REP-010-03이 들어와 재개되었다. 현재 people_count=3, status=reviewing, outcome=null이며 과거 두 명 결과와 근거 REP-010-02는 보존된다.

브라우저를 새로고침하고 서버를 재시작해도 추가 원문·진행·결과·감사 이력이 SQLite에 남는지 통합 QA에서 확인한다. seed는 첫 시작에만 불러오는 초기 사례이며 기존 업무 DB를 자동 초기화하는 자료가 아니다.

## 검증 경계

seed 제작 자체검증은 JSON·필수 필드·ID 고유성·팀 양방향 관계·현재/과거 결과 근거·시각·revision 감사 연결·음성 대본·미디어 경로를 확인한다. 독립 API/브라우저/영속성 QA는 별도 담당자가 수행한다. seed 제작 성공을 실제 구조 성과, 모델 정확도, 시간 절감의 증거로 보고하지 않는다.
